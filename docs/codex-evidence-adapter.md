# Codex Evidence Adapter v0.1

The Codex Evidence Adapter is an optional, downstream interoperability example for converting Codex execution and observability events into deterministic, privacy-minimized evidence records.

It is a community integration maintained by DigiTrans LLC. It is not affiliated with, endorsed by, certified by, or sponsored by OpenAI.

## Purpose

Codex can expose useful facts about a coding-agent run, including lifecycle events, command execution, file changes, MCP calls, token usage, and multi-agent communication telemetry. Those source events are operational data, not automatically trustworthy evidence.

The adapter applies a narrow deterministic boundary:

1. parse bounded JSONL input;
2. reject malformed input and credential-like material;
3. normalize supported fields;
4. replace free-form content, identifiers, commands, paths, tool names, prompts, and outputs with SHA-256 hashes;
5. correlate multi-agent send and receive records without inventing delivery;
6. produce scoped `EvidenceRecord` objects and an `EvidenceBundle`;
7. report source coverage and known limitations explicitly.

The adapter does not send data to a model or make a network request.

## Trust boundary

The caller supplies trusted scope through `AdapterContext`:

- `tenant_id`
- `case_id`
- `run_id`
- `created_at`
- `classification`

Codex events are treated as untrusted input. They cannot supply or override the trusted tenant, case, run, timestamp, or classification.

The adapter establishes deterministic integrity for the normalized output. It does **not** prove that the original source stream was authentic, complete, generated by an unmodified Codex runtime, or collected from a particular machine. Production provenance would require an authenticated collector, protected clock, workload identity, signed attestations, and secure storage outside the scope of this reference implementation.

## Supported inputs

### `codex exec --json`-style events

The v0.1 adapter recognizes:

- `thread.started`
- `turn.started`
- `turn.completed`
- `turn.failed`
- `error`
- `item.started`
- `item.updated`
- `item.completed`
- future additive `session.configured`, `session.catalog`, and `turn.configured` events

Known item types receive focused normalization:

- `command_execution`
- `file_change`
- `mcp_tool_call`
- `web_search`

Other supported item events are represented only by a payload hash. Unknown top-level event types are counted as ignored and are not retained.

### `codex_otel.agent_communication` events

The adapter recognizes the structured multi-agent lifecycle shape introduced by [`openai/codex#30872`](https://github.com/openai/codex/pull/30872), including:

- communication identifier;
- kind;
- send or receive state;
- sender and receiver thread identifiers;
- content presence and content hash.

A receive without a corresponding send fails closed. A send without a receive is retained but reported as partial lifecycle coverage. The adapter never converts an unmatched send into evidence of delivery.

## Privacy behavior

The generated evidence does not retain raw:

- prompts or agent messages;
- commands or command output;
- file paths;
- MCP arguments or results;
- tool, server, skill, model, thread, item, or communication names and identifiers;
- error text;
- multi-agent message content.

Those values are hash-bound when they are relevant to supported evidence. Credential-like values are rejected before hashing so a raw secret is not silently accepted into the processing path.

A deterministic SHA-256 content hash is an integrity reference, not anonymization. Predictable or low-entropy values may be discoverable through dictionary comparison. Do not publish production hashes solely because the raw value was removed; apply appropriate access control and, where needed, a deployment-specific keyed commitment layer outside this v0.1 format.

The detector covers common OpenAI API-key, AWS access-key, bearer-token, password/secret assignment, and private-key markers. It is a defense-in-depth example, not a substitute for an enterprise secret scanner.

## Evidence output

`CodexEvidenceAdapter.build_evidence()` produces three scoped records:

1. `evidence_codex_exec` — normalized execution evidence;
2. `evidence_codex_telemetry` — normalized multi-agent communication evidence;
3. `evidence_codex_coverage` — explicit availability and limitation findings.

The records are combined into one deterministic `EvidenceBundle`. Reprocessing identical inputs with the same trusted context produces the same hashes and bundle identifier.

## Coverage findings

The adapter reports these capabilities independently:

- execution event stream;
- command and file activity;
- multi-agent lifecycle correlation;
- readable multi-agent task text;
- offered tool catalog;
- offered skill catalog;
- effective permissions profile.

A field is never reconstructed merely because it would be useful. For example:

- [`openai/codex#31088`](https://github.com/openai/codex/issues/31088) documents that the JSON stream does not currently expose the complete catalog offered to the model. The adapter reports that evidence as unavailable unless an explicit catalog event is supplied.
- [`openai/codex#28058`](https://github.com/openai/codex/issues/28058) documents auditability gaps for encrypted MultiAgentV2 task content. The adapter does not treat a generic `content` field as readable task evidence. It requires an explicit `content_format: "plaintext_audit"` signal and still retains only a hash.

Support for those additive signals is forward-compatible test behavior; it is not a claim that current upstream Codex emits them.

## Local example

```bash
python -m pip install -e '.[dev]'
python examples/codex_evidence_adapter/run.py
```

The example uses only synthetic fixtures, makes no network request, and requires no OpenAI API key. Published expected files act as compatibility vectors:

- `codex_evidence_bundle.expected.json`
- `codex_coverage.expected.json`

## Security properties and non-properties

The adapter is designed to:

- fail closed on malformed JSON, orphan receives, duplicate terminal item evidence, and obvious credential-like content;
- bound line size, event count, and string size;
- hash free-form data before persistence;
- preserve explicit source limitations;
- produce deterministic output.

It does not provide:

- source authenticity;
- hardware or workload attestation;
- cryptographic signatures;
- a protected timestamp authority;
- completeness guarantees for provider logs;
- customer-data ingestion;
- OpenAI certification or endorsement.
