# Provable Agent Reference Framework v0.2.1

v0.2.1 is a security maintenance release for v0.2.0. It contains two targeted fixes, regression tests for them, and the release controls that publish them. It adds no features. v0.1.0 was not assessed for these issues.

## Security fixes

Severity ratings are pending and no CVE identifier has been assigned.

### Authorized output is now bound during standalone audit verification

`verify_audit_manifest` now compares the `output_hash` of an authorization record that is marked as authorized with the hash of the candidate's approved output: the assurance statement and the ordered limitations. A mismatch is reported as `authorization_output_mismatch`.

In v0.2.0 the check was missing. A consumer that received records as strictly JSON-serialized data and reconstructed them could be given an authorized record whose `output_hash` had been replaced and whose own `record_hash` had been recomputed to match. Standalone audit verification then reported the set as valid. Reproducing this needs only the serialized records and the public hashing rules. It does not need code execution in the consumer.

Whether this is reachable, which privileges an attacker needs, and what the impact is all depend on how the adopting application obtains and trusts its records. This is not a signature bypass and not a forgery of the whole record chain. The records are unkeyed hashes, and unkeyed hashes do not authenticate who produced them.

Denied authorization records describe the output that was requested, so they are not compared with the approved output and remain auditable.

### Canonical JSON rejects ambiguous keys and non-finite numbers

`canonical_json` and `sha256_uri` now reject any object key that is not a string, at every nesting depth, with `TypeError`. Subclasses of `str` are still accepted. In v0.2.0 the serializer silently converted integer, boolean, `None`, and float keys to strings, so `{1: "x"}` and `{"1": "x"}` produced the same canonical text and digest.

This is an input-representation ambiguity. It is not a SHA-256 collision. Decoding JSON always yields string keys, but other parsers, data transformations, and constructed Python objects can introduce non-string keys before hashing.

Non-finite numbers (`NaN`, `Infinity`, `-Infinity`) are also rejected, with `ValueError`, because they have no JSON representation.

The validation is iterative, adds no new depth limit, and leaves circular input to the serializer's existing circular-reference error. The bytes path of `sha256_uri` is unchanged.

## Compatibility

- **Python:** 3.11 and 3.12
- **Core runtime dependencies:** none
- **Record formats and hashes:** unchanged for valid inputs. Records built from string-keyed, finite-number inputs have the same canonical text and digests as v0.2.0. The regression tests pin v0.2.0 canonical text and record hashes.
- **Behavior changes:**
  - `canonical_json`, `sha256_uri`, and `authorize_exact_use` now raise for non-string keys (`TypeError`) and non-finite numbers (`ValueError`) instead of returning a digest.
  - `verify_audit_manifest` can return `authorization_output_mismatch` for tampered authorized records. Untampered records are still accepted.
- **Out of scope:** this release backports only the two fixes above. It does not add the later `main` features or other validation changes, and it adds no new public API.

## Upgrade guidance

Install the release wheel from GitHub Releases, or build from the tagged source:

```bash
python -m pip install provable_agent_reference-0.2.1-py3-none-any.whl
```

The package is not published to PyPI. GitHub release assets are the packaged artifacts.

After upgrading:

- Treat a `TypeError` about object keys as a data-quality signal. Reject the input, or convert keys with a deliberate, documented mapping that detects collisions (for example, two different keys that map to the same string). Do not convert every key with `str()`, which recreates the ambiguity.
- Treat a `ValueError` about non-finite numbers the same way: reject the input or represent the value explicitly.
- Re-run audit verification on stored records. A record reported with `authorization_output_mismatch` does not bind the output that was approved and should be investigated, not discarded.
- Keep historical records as they are. Valid records keep their hashes, so no re-hashing is needed.

If you cannot upgrade yet, compare an authorized record's `output_hash` with the hash of the candidate's assurance statement and limitations yourself, and validate that every object key is a string and every number is finite, recursively, before hashing.

## Validation gate

The release workflow runs these checks before it publishes, on Python 3.12:

- release source and metadata verification (tag format, release line, tag commit, version, release notes);
- complete unit test suite;
- dependency vulnerability audit (`pip-audit`);
- repository validation (schemas, examples, JSON, Markdown links, bytecode compilation, secret-pattern scan);
- six-case local adversarial evaluation suite;
- Ruff linting;
- source distribution and wheel build, with metadata and content validation;
- GitHub artifact attestations for the release assets.

The validation workflow runs the unit tests, dependency audit, repository validation, evaluations, linting, distribution validation, and the demo on Python 3.11 and 3.12. CodeQL and dependency review run on pull requests into the maintenance branch. This line has no database-backed components, and the gate runs none.

Automated checks are triage signals, not certification, and do not prove the absence of vulnerabilities.

## Security properties and limitations

This release narrows two ways a record set could look valid when it should not. It does not change the project's scope. The reference does not provide authenticated source collection, digital signatures or non-repudiation, protected timestamps, attestation of the producing workload, production identity or key management, or tenant isolation. Direct SHA-256 values are integrity references and do not authenticate their source.

Review the project [security policy](../../SECURITY.md), [threat model](../threat-model.md), and [open-source boundary](../open-source-boundary.md) before reuse.

Related changes: PR #29 (output binding), PR #52 (canonical keys), PR #24 (non-finite numbers).
